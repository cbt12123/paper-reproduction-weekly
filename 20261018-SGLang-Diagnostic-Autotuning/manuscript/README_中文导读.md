**方法的中文解释**

1. 给定模型、精度、负载、机器拓扑和服务目标，先列出实际版本支持的配置。
2. Agent 使用结构化指标与有来源的 trace 摘要，保留多个待检查解释。
3. 检索可能适用的诊断技能；检查技能需要的观测和干预在当前环境中能否执行。
4. 对新版本、明显变化的负载/规模或证据不足的情况，执行本地诊断重放。
5. 诊断得到支持、反驳或无法区分。它与“调优是否提高性能”是两个不同的结果字段。
6. 支持的解释帮助优先选择 P/D 资源、放置/传输或阶段内参数，具体数值交给优化器。
7. 保留合法空间中的全局探索机会，错误经验不永久排除好配置。
8. 用独立请求验证最终配置。所有诊断、部署、预热、失败和 Agent 推理都计入成本。

诊断选择公式只是一个可执行设计起点：按“区分当前解释的能力/预计代价”排序。没有可靠统计模型时采用明确的工程等级，不把 LLM 自报置信度当成概率，也不把普通打分冒充新信息论算法。阈值、评分和优化器设置需要在正式实现时固定。

**本轮最重要的文献发现**

进一步阅读了 STELLAR 与 SysInsight 的原文。两者与前一版构想的重合比最初描述更大：已有上下文规则、经验复用、规则冲突处理和实测可靠性机制。因此，本文不能把“skill 有条件”“加入反思”“规则带置信度”写成首次提出。

本稿把候选增量限制为：PD 阶段相互影响时，明确选择可区分解释的诊断动作，并将动作的观测与重放条件用于后续任务。这个机制是否比已有调优 Agent 多做了有价值的事，仍由同工具对照和消融来判定。单纯换 P800 场景不能解决新颖性问题。

**实验晚补时仍须现在确定的事**

- 核心研究问题与评价目标：不能看完结果再换主指标。
- 原生同置/PD、数值优化、固定规则、普通 Agent 与完整方案的公平条件。
- 源任务用于建库、验证任务用于阈值选择、测试任务用于最终评价的边界。
- 先报告冷启动还是带经验启动，以及建库代价如何计算。
- 所有方法相同资源上限或相同卡时预算；资源丰富不等于对完整方案免费增加并发。

文中对计时作了一个必要修正：不能预设 TTFT 等于排队＋P＋KV 传输＋D。不同实现中首 token 产生和转发路径可能不同，阶段还可能重叠；必须先确认后端的事件语义。

**编译**

在本目录运行（推荐；脚本处理 Windows 参数、BibTeX 路径和日志）：

```powershell
python build_draft.py
```

脚本会复制 BibTeX 数据到构建目录，按依赖顺序编译并检查未解析引用与越界排版。最终阅读版放在 `output/pdf`。如需重新渲染和自动检查，运行 `python check_draft.py`，再人工检查生成的 PNG。检查记录放在 `../tmp/pdfs/v0.2/qa_report.json`。

中文稿使用 XeLaTeX、ctex 与 Windows 中文字体，运行：

```powershell
python build_draft_zh.py
python check_draft_zh.py
```

中文检查额外比对中英文的章节、公式、图表数量及文献键是否一致。中文构建与检查记录放在 `../tmp/pdfs/v0.2/zh/`；仍须人工查看全部页面渲染。
